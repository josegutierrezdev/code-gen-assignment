# spec/scenarios/

Executable acceptance scenarios. Each `*.yaml` here is run by the hand-written
conformance runner (`conformance/`) against **any** combination of generated clients.

Scenarios are **platform-neutral and role-neutral**: an actor is a logical role, and the
runner decides which platform plays it (`--alice kotlin --bob python`, or every
combination with `--matrix`). A scenario MUST NOT mention a language, a path, a port, or
a platform.

## File schema

```yaml
name: alice-bob-offline          # must equal the filename stem
title: one-line human summary
requirements: [REQ-SYNC-008, …]  # core IDs this scenario exercises (traceability)
actors: [alice, bob]             # logical roles; each gets a fresh client + temp data-dir
steps: [ … ]                     # executed strictly in order
```

An actor's role name is also the messaging name it logs in with, so `login alice` is
what the `alice` actor sends.

## Steps

Every step has an `actor` plus **exactly one** action key:

| Action | Shape | Meaning |
| --- | --- | --- |
| `command` | `{actor, command: "send bob hi"}` | write one line to that client's stdin |
| `expect` | `{actor, expect: {…}, timeout_ms: 5000, capture: {…}}` | the client's **next** event must match |
| `expect_none` | `{actor, expect_none: {…}, window_ms: 1000}` | no matching event may arrive during the window |
| `kill` | `{actor, kill: true}` | terminate the process abruptly, keeping its data-dir |
| `start` | `{actor, start: true}` | relaunch with the **same** data-dir |
| `snapshot` | `{actor, snapshot: label}` | copy the data-dir aside under `label` (process must be stopped) |
| `restore` | `{actor, restore: label}` | replace the data-dir with that snapshot (process must be stopped) |

`snapshot` and `restore` both require the client to be **stopped**, so the shape is
always `kill` → `snapshot`/`restore` → `start`. Copying a live client's data-dir races
its own atomic writes (REQ-PERSIST-002) and can capture a half-written set of files.
The loader rejects a scenario that breaks this, and `ClientProcess` refuses it at
runtime too; the loader likewise rejects a `command` or `expect` aimed at a stopped
client.

### Matching is a strict transcript

`expect` consumes the client's event stream **in order**: it waits for the next event and
that event MUST match. It does not skip past unmatched events. A scenario is therefore an
exact transcript of one client's stdout, which is what REQ-COMPARE-005 requires (order is
significant within one client's stream). Extra, missing, or reordered events fail the
step.

Across actors there is no implied ordering: each actor has its own stream position, and
steps for different actors only constrain their own stream (REQ-COMPARE-005).

### Event match objects

A match is a subset of the event's fields; `type` is always required. Comparison is exact
and case-sensitive, over the fields listed in cli-contract.md §4 only
(REQ-COMPARE-001, REQ-COMPARE-004). Unlisted fields are ignored.

### Captures and `$refs`

Message ids are generated by the client, so scenarios never hard-code them
(REQ-COMPARE-008). `capture` binds a field of the matched event to a scenario variable:

```yaml
- {actor: alice, expect: {type: queued, to: bob}, capture: {m1: id}}
- {actor: alice, expect: {type: sent, id: "$m1"}}          # same client
- {actor: bob,   expect: {type: received, id: "$m1"}}       # cross-client correlation
```

Variables are scenario-global and immutable once bound. `"$name"` in any match value is
substituted before comparison.

### `kill` / `start` / `snapshot` / `restore`

These simulate crashes and lost acks, which the CLI alone cannot express:

- `kill` + `start` tests durability across a process boundary (REQ-OUTBOX-001,
  REQ-PERSIST-002), because a killed client gets no chance to flush anything.
- `snapshot` then later `restore` + `start` reproduces a **lost ack**: the client replays
  an outbox entry the server has already accepted, with the same id. That is the only
  deterministic way to drive server dedup (REQ-DEDUP-002) through the public CLI, since a
  conformant client never reuses an id on its own.
