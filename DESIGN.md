# Design

## The spec is authoritative, and that rule has teeth

All behaviour lives in `spec/core/` as 181 numbered requirements (`REQ-<AREA>-NNN`) in
RFC 2119 language. `CLAUDE.md` forbids answering a behaviour question by reading
`clients/` — existing generated code has no authority. Generated files must carry a
`GENERATED from spec/` header and cite the requirement IDs they implement, so every line
of output is traceable back to a sentence of input, and `GENERATION_REPORT.md` records
the spec checksums the output was built from.

The rule that matters most: **if the spec is ambiguous, the run stops and reports the
ambiguity** rather than guessing. A stopped run with a precise question is a success; a
run that guessed is a failure even if it goes green.

## A JSONL CLI as the observable contract

Both clients expose exactly one interface: commands in on stdin
(`login`/`send`/`offline`/`online`/`quit`), JSON Lines events out on stdout
(`ready`, `logged_in`, `state`, `queued`, `sent`, `received`, `error`), human logging on
stderr. Field names and enum values are exact and case-sensitive.

This is what makes the clients comparable at all. The runner never inspects a client's
internals, files, or language — it writes lines and reads lines. Any language that can do
that can be a target platform.

## Conformance as the oracle

`conformance/` is hand-written and is the definition of done: a client is not finished
until `python scripts/conformance.py <platform>` exits 0. Scenarios in
`spec/scenarios/*.yaml` are platform- and role-neutral, so the runner can cast either
client as either participant — `--matrix` runs every combination, which is how
"interchangeable" gets proven rather than asserted.

Matching is a **strict transcript**: each `expect` must match the *next* event on that
client's stream. An extra, missing or reordered event fails. That catches the bugs a
"wait until you see X" matcher would silently skip.

Two scenario actions exist because the CLI alone cannot express them: `kill`/`start` for
crash durability, and `snapshot`/`restore` to reproduce a lost ack — the only
deterministic way to drive server dedup through the public interface, since a conformant
client never reuses an id. Both must happen with the process stopped, enforced at load
time.

## Idempotent ids

A UUIDv4 generated by the sending client at the moment the user sends is the dedup key
end to end: sender outbox, server store, recipient inbox. A retransmission reuses it. The
server treats a repeated `send` as success — re-ack, never store or forward twice — which
is what lets a client retry blindly after any reconnect without inventing an
at-most-once protocol. Delivery is at-least-once on the wire and exactly-once observable,
because the recipient dedupes on the same key.

## welcome → replay → sync_done → flush

The one ordering that makes offline delivery observable and testable:

```
hello → welcome{pending:N} → N held msgs in original order → sync_done → then flush
```

The client must not flush its outbox until `sync_done`. Without this, a reconnect
interleaves replayed inbound messages with outbound retries and no test can assert
anything stable. With it, the whole offline story is a deterministic transcript — which
is exactly what `alice-bob-offline` asserts, and why a held message provably arrives
*before* the recipient's own queued message is acked.

The server holds a message until the recipient sends `delivered{id}`; pushing is not
deleting. No timeout or disconnect may drop a message.

## Core vs platform profiles

`spec/core/` is platform-neutral and says nothing about languages or build systems.
`spec/platforms/<name>.md` holds only idioms, libraries and build commands, and states
explicitly that it defines no behaviour and that core wins on conflict. This keeps the
hard part — behaviour — written once, and makes adding a platform a matter of one
profile plus one manifest.

The split is load-bearing in places that would otherwise diverge silently: text length
is specified in **Unicode code points**, so Python's `len()` is already correct while
Kotlin must use `codePointCount` rather than `String.length`.

## Per-OS manifest env, and the Windows TEMP finding

`platforms/*.yaml` carries `build_cmd`/`run_cmd` with `posix:` and `windows:` variants
plus an optional `env:` block, with a `${repo_root}` placeholder so nothing
machine-specific is committed. The harness merges that env for builds and client
launches, so no manual setup is needed.

That block exists because of a concrete finding worth recording. Gradle died with:

```
java.io.IOException: Unable to establish loopback connection
Caused by: java.net.SocketException: Invalid argument: connect
```

It reads like a networking fault and is not one. A Gradle build runs in a daemon JVM, and
**JDK 16+ backs its NIO pipes with an AF_UNIX socket *file* in the temp directory** — so
an unwritable or full temp volume breaks every build with a message that names neither
temp nor disk. Isolated by bisecting the environment: with `TEMP` on the bad volume the
build fails, with `TEMP` redirected it succeeds, and `GRADLE_USER_HOME` makes no
difference either way. Hence `TEMP`/`TMP` → `${repo_root}/.gradle-tmp` in the manifest.

One related harness bug, same family: on Windows `CreateProcess` resolves a relative
`argv[0]` against the *parent's* working directory, not the `cwd` handed to `Popen`, so a
relative `run_cmd` vanished with `WinError 2`. The manifest loader now absolutises a
relative launcher against `out_dir`, which keeps manifests readable and portable.
